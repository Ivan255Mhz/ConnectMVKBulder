# Глава 1. Введение и обзор

Эта глава — обзорная. В ней: что такое устройство МВК01, какие задачи решает
библиотека `ConnectMVKBulder`, из каких слоёв она состоит, как её собрать и как
читать это руководство. Практика начинается со [главы 2](02-getting-started.md),
поэтому код здесь сведён к минимуму.

## 1.1. Что такое МВК01

**МВК01** — многоканальный виброконтроллер с интерфейсом **Modbus/TCP**.
Устройство измеряет вибрацию по 8 каналам АЦП (виброускорение, виброскорость,
виброперемещение), принимает сигналы двух каналов тахометров и рассчитывает
дольоктавный спектр из 43 полос. Результаты контроля сравниваются с настроенными
зонами (зелёная, жёлтая, красная), состояние каналов и агрегатов доступно по
регистрам Modbus.

С точки зрения интеграции МВК01 — обычный Modbus/TCP-slave:

- TCP-порт по умолчанию — `502`, идентификатор устройства (SlaveId) — `1`;
- чтение — функциями `0x03` (holding registers) и `0x04` (input registers);
- запись — функциями `0x06` и `0x10`;
- максимальный размер запроса — 125 регистров.

Основная сложность — не в протоколе, а в **карте регистров**. Чтобы получить
осмысленное значение, нужно знать адрес, число регистров, порядок байт и правила
декодирования. Ключевые особенности МВК01:

| Особенность | Следствие для клиента |
|---|---|
| Принимаются только чётные адрес и количество регистров | запрос с нечётным адресом или количеством отклоняется (ответ-исключение Modbus `0x01`) |
| 32-битные значения (`float`/`uint`) занимают 2 регистра | порядок байт задаётся регистром `0x000C`: `BigEndian` (по умолчанию), `Mixed` (для ВДМ82), `LittleEndian` |
| Расчётные параметры адресуются по номерам | адрес = `0x4000 + (N−1)×16`; например, N = 48 → `0x42F0` |
| Строки каналов (единицы измерения, серийные номера датчиков) хранятся с обратным порядком байт внутри 4-байтных слов, кодировка cp1251 | прямое чтение даёт нечитаемый текст, нужен swap байт внутри слов |
| Версия внутреннего ПО упакована в `uint32` | `0x01071400` → `1.7.20.0` |

Транспорт и карта регистров проверены на реальном устройстве
**10.20.0.211:502** (ПО 1.0.67.1, SlaveId 1, BigEndian). Первоисточник по
адресам — [MVK01_registers.txt](../MVK01_registers.txt).

## 1.2. Какие задачи решает библиотека

Если писать Modbus-клиент «с нуля», каждый проект заново решает одни и те же
задачи: открыть сокет, выставить таймауты, переподключиться после разрыва,
сериализовать запросы, защитить конфигурационную область от случайной записи,
разобрать `float` из регистров, не забыть освободить ресурсы. `ConnectMVKBulder`
закрывает этот слой целиком.

| Задача | Решение в библиотеке | Проект |
|---|---|---|
| Обмен по Modbus/TCP, таймауты, ленивое подключение | `NModbusTransport` (на базе NModbus 3.0.81) | `Mvk.Modbus` |
| Несколько устройств, реконнект, простой, события | пул `MvkDevicePool`, `IMvkDevice` | `Mvk.Modbus` |
| Настройки из JSON, значения по умолчанию, проверка | секция `MvkModbus`, `MvkModbusOptionsLoader`, валидатор | `Mvk.Modbus` |
| Единая обработка каждого запроса | пайплайн `IModbusMiddleware` | `Mvk.Modbus` |
| Декодированные значения МВК01 и системные команды | фасад `Mvk01Device`, `Mvk01Connection`, `Mvk01RegisterMap` | `Mvk.MVK01` |
| Периодический опрос без ручного цикла | `Mvk01Watcher`, `IAsyncEnumerable<Mvk01Sample>` | `Mvk.MVK01` |
| Прикладные уставки и реакции на тревоги | `Mvk01AlarmService`, `MvkSetpointEngine`, JSON/fluent | `Mvk.MVK01` |
| Тесты без железа | эмулятор `MvkTestServer`, `FakeModbusTransport` | `tests/Mvk.Testing` |

Библиотека не является «драйвером всего МВК01»: она покрывает транспорт,
конфигурацию и типовые измерения, а расширенную диагностику можно реализовать
поверх сырого чтения регистров.

## 1.3. Возможности

- **Ленивое подключение.** Соединение открывается в момент первого запроса
  (или явного `EnsureConnectedAsync`) и не тратит ресурсы, пока устройство не
  нужно.
- **Автореконнект с экспоненциальным backoff.** При транспортной ошибке
  устройство переходит в `Faulted` и переподключается с задержкой от
  `ReconnectBaseDelayMs` до `ReconnectMaxDelayMs`; вызывающий код получает
  ошибку, но не занимается восстановлением связи.
- **Idle-отключение.** После `IdleDisconnectSeconds` простоя (по умолчанию 120 с)
  фоновый цикл закрывает соединение; сокеты держат только активные устройства.
- **Сериализация запросов.** Запросы к одному устройству выполняются по очереди
  (`MaxConcurrentRequests`, по умолчанию 1) — искусственные паузы между вызовами
  не нужны.
- **Пайплайн middleware.** Каждый запрос проходит цепочку в стиле ASP.NET:
  `timeout`, `logging`, `metrics`, `validation`, `retry`, `writeProtection`.
  Состав и порядок задаются списком `Pipeline`; можно добавить свой middleware.
- **JSON-конфигурация с валидацией.** Секция `MvkModbus` с настройками по
  умолчанию (`Defaults`), списком устройств (`Devices`) и настройками пула
  (`Pool`). Ошибки (дубли `Id`, пустой `Host`, недопустимые диапазоны)
  обнаруживаются при старте хоста или при загрузке файла.
- **Интеграция с DI.** `AddMvk01` (сразу пул + типизированный слой),
  `AddMvkModbus`, `AddMvk01Devices`, `AddMvk01Alarms`, `AddMvkModbusHostedService`,
  `AddModbusMiddleware<T>("имя")` — регистрация пула, типизированного слоя,
  уставок и собственных обработчиков.
- **Типизированное чтение МВК01.** Снимок канала (`SensorVoltage`, `Spectrum`
  из 43 полос, `RmsSets`, `State`), снимок тахометра, сведения об устройстве,
  конфигурация канала, значения параметров по номерам для всех 8 каналов.
- **Системные команды.** Save (`0xF0001`), Restore (`0x10001`), Reboot
  (`0xA0001`) с ожиданием статуса и расшифровкой результата.
- **Компактные операции.** `ReadValueAsync`/`ReadValuesAsync`/`WatchAsync`/
  `ReadChannelSnapshotAsync` на `Mvk01Connection` и `IMvk01Device`, `AddMvk01`
  одним вызовом.
- **Объединённые чтения.** Снимок канала — 3 запроса вместо 5, сведения об
  устройстве и конфигурация канала — по 1, наблюдатель — до 7 параметров на
  запрос; согласованность снимка проверяется по копиям регистров.
- **Наблюдение и уставки.** `Mvk01Watcher` отдаёт сэмплы, `MvkSetpointEngine`
  оценивает прикладные пороги с гистерезисом и задержкой, `Mvk01AlarmService`
  объединяет устройства и отдаёт события тревог.
- **Эмулятор для тестов.** `MvkTestServer` (Modbus-slave на loopback),
  `SilentTcpServer` (проверка таймаутов), `FakeModbusTransport` (запрограммированные
  ответы и журнал запросов) — юнит-тесты без реального железа.

## 1.4. Архитектура

Библиотека разделена на два уровня. Нижний (`Mvk.Modbus`) ничего не знает о
специфике МВК01: это транспорт, конфигурация, пул и пайплайн для любого
Modbus-совместимого устройства. Верхний (`Mvk.MVK01`) знает карту регистров
МВК01 и предоставляет типизированные вызовы.

```
Mvk.Modbus
  Транспорт  →  Пайплайн  →  Пул
  (сокет)       (middleware)  (устройства, состояния, реконнект)

Mvk.MVK01
  Карта регистров / кодеки  →  Фасад устройства  →  Наблюдение  →  Уставки
  (адреса, декодирование)      (Mvk01Device,          (Mvk01Watcher)  (Mvk01AlarmService)
                                Mvk01Connection, фабрика)
```

Поток одного запроса от прикладного кода до сокета:

```
IMvk01Device (Mvk.MVK01)                  типизированные значения, команды
    |
    v
IMvkDevice (Mvk.Modbus.Pool)              очередь запросов, состояние, реконнект
    |
    v
middleware (Mvk.Modbus.Pipeline)          timeout -> logging -> metrics ->
    |                                     validation -> retry -> writeProtection
    v
NModbusTransport (Mvk.Modbus.Transport)   NModbus 3.0.81, таймауты, ленивое подключение
    |
    v
TCP-сокет :502                            Modbus/TCP -> устройство МВК01
```

Как это читать:

1. **`IMvk01Device` / `Mvk01Device`** — типизированный фасад. Метод
   `ReadChannelAsync(1)` сам решает, какие регистры прочитать, и возвращает
   готовый `Mvk01Channel` с декодированными значениями. Здесь же выполняются
   системные команды.
2. **`IMvkDevice` / `MvkDevice`** — устройство пула. Принимает уже готовый
   `ModbusRequest`, сериализует запросы через семафор, ведёт состояние
   (`Disconnected`/`Connecting`/`Connected`/`Faulted`), планирует реконнект.
   Именно на этом уровне живёт «счастливый путь»: `ExecuteAsync` возвращает
   ответ даже с ошибкой, а удобные обёртки чтения/записи выбрасывают
   `MvkModbusException`.
3. **Пайплайн middleware** — обработчики вокруг транспорта. `validation`
   проверяет корректность запроса (для МВК01 — чётность адреса и количества),
   `retry` повторяет временные ошибки, `writeProtection` не даёт записать в
   защищённую область, `timeout` ограничивает общее время операции.
4. **`NModbusTransport`** — единственное место, где используется NModbus.
   Открывает `TcpClient`, настраивает таймауты чтения/записи, преобразует
   `ModbusRequest` в вызовы NModbus и обратно.
5. **Сокет** — собственно Modbus/TCP-обмен с устройством.

`IModbusMiddleware`), а не с типами NModbus.

## 1.6. Требования и сборка

- .NET SDK 8.0+ (решение собрано и проверено на SDK 10, рантайм 8.0);
- реальное устройство МВК01 в сети — для проверок (по умолчанию в примере
  `10.20.0.211:502`, SlaveId 1). Для автотестов железо не нужно: используется
  эмулятор.

```powershell
dotnet build ConnectMVKBulder.sln                      # сборка
dotnet test                                            # тесты
dotnet run --project samples\Mvk.Sample.Console        # обзор устройства (DI-пример)
dotnet run --project samples\Mvk.Sample.Polling        # опрос СКЗ 10…1000 Гц каждые 0,5 с
```

Проверить доступность устройства перед запуском примеров:

```powershell
Test-NetConnection 10.20.0.211 -Port 502
```

## 1.7. Принципы простоты

Публичный API библиотеки проектировался по обязательным принципам:

- простейший сценарий — три строки: `Mvk01Connection.ConnectAsync(host)` →
  `ReadChannelAsync(1)` → декодированные значения;
- все параметры (порт 502, SlaveId 1, BigEndian, таймауты, ретраи, автореконнект)
  имеют рабочие значения по умолчанию;
- один вызов `ReadChannelAsync` = полный снимок канала; запросы к устройству
  библиотека делает сама (чанки не более 125 регистров);
- значения декодированы (float, строки, битовые поля, статусы) — никаких
  ручных `BitConverter` в прикладном коде;
- ошибки — одно исключение `MvkModbusException` с понятным текстом; связь
  восстанавливается автоматически;
- JSON-конфиг и middleware опциональны: минимальный конфиг устройства —
  `{ "Id", "Host" }`;
- «сложный» API (пул, пайплайн, сырые регистры) доступен, но не обязателен;
- публичные API только асинхронные; синхронные обёртки не добавляются.

Эти принципы объясняют структуру руководства: сначала простые сценарии, затем —
управление сложностью.

## 1.9. Меры предосторожности

Библиотека умеет и читать, и писать регистры, поэтому важно разделять сценарии
по риску.

- **На реальном устройстве без явного разрешения выполняйте только чтение.**
  Запись регистров конфигурации, `SaveConfigurationAsync`, `RestoreConfigurationAsync`
  и `RebootAsync` меняют состояние железа и могут нарушить работу стенда.
- По умолчанию `WritePolicy` = `ProtectConfigArea`, а `AllowConfigurationWrite` =
  `false`: запись в область `0x0000–0x0FFF` (конфигурация) запрещена. Явное
  разрешение включается в конфигурации устройства (`AllowConfigurationWrite: true`)
  или параметром `ConnectAsync(..., allowConfigurationWrite: true)`
  (нужно для системных команд).
- Системная команда `SaveConfiguration` может отвечать до 3 секунд — библиотека
  автоматически подставляет таймаут операции и ждёт статус; не запускайте
  сохранение в цикле.
- Все примеры этого руководства, запускаемые на реальном устройстве,
  ограничиваются чтением, если явно не сказано обратное.
- Проверяйте доступность устройства и не опрашивайте его чаще, чем нужно:
  для МВК01 безопасен опрос раз в 0,5 с, но без необходимости лучше реже.

## Подводные камни

- **Карта регистров в `MVK01_registers.txt` составлена для ПО 1.0.61**, а на
  стенде проверено ПО 1.0.67.1. При расхождениях ориентируйтесь на фактическое
  поведение устройства и на `Mvk01RegisterMap`.
- **В документе есть ошибка**: для N = 48 указан адрес `0x41F0`, фактически
  параметр находится по адресу `0x42F0` (`0x4000 + (48−1)×16`).
- **Синхронного API нет** — только async-методы с `CancellationToken`. Любые
  попытки `.Result`/`.Wait()` в UI-потоке приведут к блокировке.
- **`Mvk.Modbus` не знает про МВК01.** Разделение слоёв принципиально: типизация,
  кодеки и адресация — в `Mvk.MVK01`.
- **`ExecuteAsync` не бросает исключение при ошибке устройства**: ответ приходит
  с заполненным `Error`. Удобные обёртки (`ReadHoldingRegistersAsync` и т.п.),
  наоборот, выбрасывают `MvkModbusException`. Не смешивайте контракты.
- **Отмена — это не ошибка транспорта.** `CancellationToken` приводит к
  `OperationCanceledException`, а не к `MvkModbusException`.
- **Ветка `dev` — основная ветка разработки**; в `main` изменения попадают
  только по явному запросу.
